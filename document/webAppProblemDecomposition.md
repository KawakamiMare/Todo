# Webアプリ開発：詰まった時の切り分けフレーム

- 作成日：2026年5月11日
- 目的：詰まった時に「何が分からないか」を分類し、最短で次の行動（調べ方・検証）に落とす

---

## まず結論：分類できると「調べ方」が変わる

Webアプリ開発で詰まった時は、問題を次の分類にラベリングすると頭が整理される。

- **言語知識**
- **フレームワーク**
- **設計**
- **アーキテクチャ**
- **ライブラリ**

加えて実務では、上の5つに入り切らない（が超重要）な横断軸がある。

- **環境/運用（Dev環境・ビルド・設定・デプロイ）**
- **デバッグ技術（再現・観測・切り分け手順）**
- **データ/永続化（DB・トランザクション・性能）**（※設計とも重なるが独立して詰まりやすい）
- **ドメイン（業務知識・仕様）**

このドキュメントは「分類 → 典型症状 → 観測ポイント → 次アクション」までをセットにする。

---

## 分類の定義（“粒度”で分ける）

### 設計 vs アーキテクチャ（ここが一番混ざりやすい）

- **設計（ミクロ）**：関数/クラス/メソッド/1ファイルの責務分離や依存の向き、命名、テストしやすさ
- **アーキテクチャ（マクロ）**：システム全体やチームの境界の決め事（層、分割単位、通信、非機能要件）

例：

- Controllerにロジックを書きすぎた → 最初は**設計**
- それが毎回起きる/レビューで防げない → **アーキテクチャ**（ルール化・境界ルールの不在）に昇格

---

## 早見表：分類ごとの「症状」「観測」「次アクション」


| 分類      | 典型症状（詰まり方）                        | まず見る/確認する                   | 次アクション（調べ方の型）                   |
| ------- | --------------------------------- | --------------------------- | ------------------------------- |
| 言語知識    | 文法/型/例外/非同期が分からず書けない・読めない         | どの構文/型エラーで止まっているか（最小例にできるか） | 公式仕様・入門書・「最小再現コード」で理解する         |
| フレームワーク | 「流儀」が分からない（ライフサイクル、DI、ルーティング等）    | FWが“いつ/どこで”呼ぶか（ライフサイクル）     | 公式ドキュメントの該当章 + サンプルを写経→改造       |
| 設計      | どこに書くべきか、責務が混ざり保守できない             | 「この関数の責務は一言で？」が言えるか         | 責務を分解し、依存方向（上位→下位）を整える          |
| アーキテクチャ | 境界が曖昧で全体が壊れやすい、変更の影響範囲がデカい        | “境界”がどこか（FE/BE、層、モジュール）     | 境界ルール（例：Controllerは薄い等）を明文化する   |
| ライブラリ   | README通りに動かない、設定が分からない、罠にはまる      | バージョン、設定、制約、既知のIssue        | README/Docs/Issue検索 + 最小サンプルで検証 |
| 環境/運用   | 起動しない、ビルドできない、依存が壊れる、CORS、デプロイ不整合 | ログ、環境変数、設定ファイル、依存解決         | 変更点の差分を洗い出し、再現条件を固定する           |
| データ/永続化 | 直感と違う更新、整合性、N+1、遅い、ロック            | SQL、インデックス、トランザクション境界       | クエリ可視化 → 仮説（原因候補）ごとに検証する        |
| ドメイン    | 仕様が決められない、例外ケースが漏れる               | 用語定義、入力/出力、業務ルールの例外         | 仕様を文章+具体例（境界値）に落とす              |

## 「詰まり」を診断するための最短フロー

### 0. まず“デバッグ技術”で「観測できる状態」を作る

分類の前に、次の3点を揃える（これが無いと永遠に迷走しやすい）。

- **期待値**：本当はどうなるべき？
- **現状**：実際はどうなってる？（ログ/画面/HTTP/DBなど“観測可能”に）
- **仮説**：なぜそうなったと思う？（原因候補を2〜3個に絞る）

テンプレ：

- 期待値：
- 現状：
- 仮説：
- 試したこと：
- 次に切りたい論点：（例：通信は成功しているか？／フロントが受け取れているか？）

### 1. 位置の特定（どの境界で壊れているか）

「フロントか？バックか？」の前に、まず“境界”を一つずつ確認する。

- **(A) 通信**：Networkでステータス/レスポンス中身/想定フィールドを確認
- **(B) 受け取り**：フロント側でレスポンスを受けているか（ログ/例外/型）
- **(C) 状態更新**：state/storeに値が入ったか
- **(D) 表示**：表示条件・再描画（メモ化/キャッシュ）で落ちてないか
- **(E) 永続化**：DBに入ったか、読めているか

### 2. ラベリング（原因の種類を決める）

原因が見つかった“場所”に応じて分類する（例）。

- React Queryでキャッシュが残り、POST成功でも一覧が変わらない → **ライブラリ**（＋フレームワーク）
- SpringでJSONシリアライズが想定と違う → **フレームワーク**
- 型の付け方が分からずnullが混ざる → **言語知識**
- Controllerにロジックが散らばり追えない → **設計**
- FE/BE間の契約（フィールド名や形式）が毎回ずれる → **アーキテクチャ**（契約の運用）

## よくある具体例（分類の練習）

### APIは200なのに画面が更新されない

最初の分類は **アーキテクチャ** ではなく、まず **デバッグ技術**（観測の順序）に置くと速い。

- (A) レスポンスJSONが想定と一致？（キー名・型・配列/オブジェクト）
- (B) フロントで例外出てない？（コンソール）
- (C) state/store更新できてる？（setStateの実行、キャッシュ）
- (D) 表示条件が一致？（filter条件、mapのkey、メモ化）

原因が見つかったら、その時点で（言語/FW/設計/アーキ/ライブラリ）に確定ラベルを付ける。

## 次に学ぶと繋がるテーマ（おすすめキーワード）

- 設計：**責務分離 / 関心の分離 / 依存関係逆転（DIP） / 単一責任（SRP）**
- アーキテクチャ：**レイヤード / モジュラモノリス / API契約（Schema）/ 非機能要件**
- デバッグ：**最小再現 / ログ設計 / 二分探索的デバッグ / 観測可能性（Observability）**
- データ：**トランザクション / インデックス / N+1 / ロック**
